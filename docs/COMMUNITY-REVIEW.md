# 社区投稿审核与版本流程

## 从一句创意到可安装更新

| 状态 | 谁处理 | 通过标准 |
| --- | --- | --- |
| `needs-info` | 投稿人 | 补齐用户、交互、桌面／手机截图、联网与隐私说明 |
| `awaiting-review` | 维护者 | 不重复已有能力，第一次打开可理解，数据边界合理 |
| `invited-pr` | 投稿人或智能体 | 生成最小改动，关联投稿 Issue，不携带私人数据 |
| PR 自动校验 | GitHub Actions | 模板、模块、目录、测试、站点与扩展构建全部通过 |
| PR 人工审核 | 维护者 | 桌面／手机／离线可用，权限最小，失败可恢复 |
| 已发布 | 维护者 | 进入固定来源的公共目录，并写入发布说明 |

自动检查通过只说明投稿信息完整。新联网源、浏览器权限、同步协议、数据迁移和可执行代码必须人工复核；来源、更新时间、错误与离线缓存必须在界面中可见。

## 审核重点

1. **有用**：用户第一次打开就能完成一个具体任务，不是不可操作的展示卡。
2. **可修改**：作者示例全部可改、可删、可恢复，不把作者生活数据写死。
3. **最小权限**：默认本地保存；联网只访问声明的数据源，不索取无关权限。
4. **可降级**：网络失败仍能打开工作台，并说明正在显示缓存还是尚无数据。
5. **同一产品**：网页、离线 HTML、PWA 和新标签页扩展保持同一核心体验。
6. **可维护**：唯一 ID、依赖、来源、版本和破坏性迁移写清楚。

## 版本与更新约定

- OneBench 发布版本使用 `主版本.次版本.修订号`；浏览器扩展必须使用 1–4 段纯数字版本。
- 内置条目可以跟随 OneBench 发布；第三方条目进入目录时必须固定到 commit SHA 或不可变版本标签，不能使用 `main`、`master` 或 `latest`。
- 修订版本只做兼容修复；次版本可新增模块或字段但必须保留旧数据；主版本允许不兼容变化，但必须提供迁移说明和回退方法。
- 模块市场只下载经校验的目录元数据，不直接执行第三方代码。升级由用户或智能体展示差异、备份、测试后完成。

## 维护者合并清单

- 投稿 Issue 与 PR 相互关联，类型和文件范围一致。
- CODEOWNERS 指定的维护者已经批准安全边界与发布文件。
- 自动检查全部通过；桌面、手机、离线和刷新后持久化均有证据。
- 发布说明写明新增能力、权限变化、数据迁移和回退方式。
